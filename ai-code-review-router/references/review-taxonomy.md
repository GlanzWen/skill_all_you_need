# Review 分类体系

## 严重度

| 等级 | 含义 | 人工动作 |
| --- | --- | --- |
| P0 | 可能导致安全事故、资损、数据破坏、核心链路不可用、明显破坏兼容性 | 阻断合并，必须深审 |
| P1 | 可能导致业务结果错误、状态污染、统计误导、线上性能明显退化、接口调用方受影响 | 合并前必须确认 |
| P2 | 可能导致局部缺陷、边界条件失败、可观测性下降、维护成本明显升高 | 建议修复或补验证 |
| P3 | 可读性、样式、重复代码、轻微测试缺口、低风险生成代码 | 抽查或批量确认 |

## 风险域

| 风险域 | 触发线索 | 常见人工问题 |
| --- | --- | --- |
| 业务语义 | service、manager、workflow、domain、规则判断 | 是否改变业务口径；是否覆盖异常路径 |
| 数据/SQL | mapper、SQL、DAO、索引、分页、统计 | 口径是否正确；是否会扫大表；是否需要对账 |
| 接口兼容 | controller、DTO、client、Dubbo、OpenAPI、proto | 入参/出参是否兼容；调用方是否同步 |
| 状态机 | status、state、transition、lifecycle、cancel、retry | 非法迁移是否被挡住；失败/取消是否污染成功 |
| 并发/幂等 | lock、retry、queue、MQ、scheduler、async | 重试是否幂等；并发写是否冲突 |
| 鉴权/安全 | auth、permission、session、cookie、token、sign、cors | 是否越权；密钥是否泄露；跨域是否安全 |
| 配置/发布 | application.yml、bootstrap、Dockerfile、pom、package、feature flag | 默认值是否安全；灰度和回滚是否明确 |
| 前端交互 | React/Vue、表单、路由、状态管理 | 是否破坏关键流程；移动端/错误态是否覆盖 |
| 测试缺口 | test、spec、mock、fixture | 高风险逻辑是否缺少最小验证 |
| 生成/样板 | generated、schema output、批量 DTO、纯格式化 | 抽样是否能证明生成模式正确 |

## 证据等级

| 等级 | 可写结论 |
| --- | --- |
| 已验证 | 有具体命令、退出码、日志或测试结果支持 |
| 静态代码证据 | 有文件、行号、函数、SQL id、配置 key 等直接证据 |
| 代码推断 | 根据调用链或控制流推断，但未运行验证 |
| 需要人工确认 | 依赖业务口径、数据分布、发布策略或外部系统 |
| 低置信怀疑 | 线索不足，只能提示人工抽查 |

## 自动分类校正原则

- 高严重度必须有明确证据；没有证据时降为“需要人工确认”。
- 大文件不等于高风险；核心链路小改动也可能是 P1。
- 测试文件变更不能抵消生产代码风险，只能作为验证证据之一。
- 纯格式化、生成代码、批量搬迁优先折叠，但必须抽样确认生成模式。
- 对 AI 生成代码尤其关注“看起来完整但缺少异常路径”的问题。
